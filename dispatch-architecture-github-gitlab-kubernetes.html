Summary

The repository deployments use CI to deliver source events, orchestrate agent runs, and supply execution context. GitHub uses reusable Actions workflows and GitLab currently uses scheduled polling and API-triggered pipelines. Jira is an existing tracker source. These sources remain responsible for entity state and permissions.

Proposal The centralized Kubernetes deployment retains source adapters, normalization, authorization, harness selection, and fullsend run. Fullsend takes responsibility for coordinating discovery through run admission; a trusted launcher creates Kubernetes Jobs. The pilot uses a single poller and dispatcher with direct candidate handoff. Active-active operation adds shared durable coordination around the same selection and launch logic. A webhook receiver can become another candidate producer without becoming another dispatcher.

The plan is to evolve existing Fullsend components: keep repository installations working, separate discovery from launch, adapt selection for independently evaluated contexts, and add a centralized launcher around the existing runner. A Job Pod and its remote OpenShell sandbox are distinct workloads.

Terms used below
  • Candidate reference: source, entity, and stable provider observation identity; no credentials or full source payload.
  • Normalized evaluation input: current entity/activity and actor evidence prepared for selection.
  • Selected run: one authorized agent/context choice with target and output destination.
  • Job / Pod: Kubernetes workload object and its execution instance. A replacement Pod can repeat program execution.
  • Sandbox: isolated remote OpenShell workspace, distinct from the Job Pod.
  • Result: application outcome and configured output, retained independently of workload cleanup as required.

Two-phase deployment view

Pilot: direct handoff, one service instance

Source poller → candidate handoff → one dispatcher (normalize, select, admit) → launcher/API → run Job → remote sandbox gateway.

Filesystem manifest/configuration feeds source selection, authorization, and workload policy. Direct handoff is a logical contract; it does not require a new public API or a network hop. The pilot requires one poller and one dispatcher, one selected source, direct handoff, and no mandatory database or broker. The unresolved persistence and acknowledgement mechanism must still make accepted responsibility recoverable.

Webhook ingestion and active-active scaling are separate extensions after the candidate and run contracts are stable.

Active-active: shared responsibility, same selection core

Poller replicas and optional webhook receiver → shared durable inbox → dispatcher replicas → recoverable run records/idempotent launcher → Jobs.

Checkpoint coordination and optional source-query leases sit beside producers. Selection, authorization, and launch policy remain the same. Inbox, run records, and leases are logical responsibilities, not a commitment to three products or any storage technology. An inbox delivery and a Kubernetes create are not one atomic transaction.

The shared coordination layer must recover claims, partial fan-out, ambiguous creates, retries, backlog progress, and selected-run history.

State, identity, and recovery

There are two acceptance boundaries. A producer may acknowledge a candidate only after responsibility for that candidate can be recovered. A dispatcher may acknowledge handling only after every selected run is recoverably admitted, or a terminal no-match/rejection is recorded. In inbox mode, durable enqueue can accept before selection; consumer acknowledgement follows recoverable handling.
