Summary

The repository deployments use CI to deliver source events, orchestrate agent runs, and supply execution context. GitHub uses reusable Actions workflows and GitLab currently uses scheduled polling and API-triggered pipelines. Jira is an existing tracker source. These sources remain responsible for entity state and permissions.

Proposal The centralized Kubernetes deployment retains source adapters, normalization, authorization, harness selection, and fullsend run. Fullsend takes responsibility for coordinating discovery through run admission; a trusted launcher creates Kubernetes Jobs. The MVP uses one poller CronJob and one dispatcher CronJob, each performing bounded work and exiting. PostgreSQL retains candidate responsibility and run state between invocations. Agent Jobs execute independently and remain until a later dispatcher invocation records their outcomes and deletes them. A separate message broker is not required; concurrent workers and source partitioning are deferred. A webhook receiver can become another candidate producer without becoming another dispatcher.

The plan is to evolve existing Fullsend components: keep repository installations working, separate discovery from launch, adapt selection for independently evaluated contexts, and add a centralized launcher around the existing runner. A Job Pod and its remote OpenShell sandbox are distinct workloads.

🗡️ Proposed Kubernetes binding: tenant trust, service-account convention, and GitHub installation access

Proposed At tenant onboarding, service operators configure the mint to trust a cluster issuer and tenant namespace for specific GitHub App installations and role ceilings. Repository owners control which repositories those installations can access through GitHub. The service-account naming convention identifies the repository and role within that tenant boundary.

Mint policy, established at tenant onboarding:
  trusted cluster issuer + tenant namespace
    → permitted GitHub App installation(s) + role/permission ceilings

Signed Kubernetes identity, interpreted by convention:
  sub = system:serviceaccount:fullsend-team-a:fs-repo-123456-coder
    → repository ID 123456 + Coder role

Mint request to GitHub:
  tenant’s permitted installation + repository_ids: [123456]
    + explicit role-limited permissions → scoped installation token

The mint validates the projected JWT against the registered issuer’s signing keys, audience, and validity period. It derives namespace and service-account identity from signed claims, checks their consistency, and strictly parses the agreed naming format. Use stable GitHub repository IDs and registered role names; reject malformed names, unknown roles, and requested scopes that exceed the identity or tenant policy. The caller cannot choose another tenant’s installation.

Every token request to GitHub specifies the repository and permissions. GitHub rejects access beyond the installation’s repository selection or granted permissions; omitting repository scope would request installation-wide access. The mint relies on that current installation boundary instead of maintaining a second repository allowlist. See GitHub installation-token scope.

Dispatcher responsibility. The Kubernetes launcher ensures the required service accounts exist before creating Jobs, using trusted dispatcher configuration to choose each tenant namespace and repository/role identity. The accounts persist across runs and are not owned by individual Jobs. Unexpected existing accounts fail validation rather than being silently adopted. Authorization follows the account name, not its UID: recreating the same account intentionally restores the same authority without a mint update. Retiring unused accounts is a separate reconciliation operation that must account for active Jobs.

Repository onboarding. The tenant grants the relevant GitHub Apps access to the new repository, if needed, and updates the dispatcher configuration for its next invocation. The launcher creates the required accounts. There is no per-repository mint configuration, dispatcher-to-mint enrollment call, or mint redeployment. Changes to a tenant’s trusted issuer, namespace, installations, or role ceilings still require a tenant-policy update.

Delegated authority. The dispatcher may create identities for any repository covered by that tenant’s permitted installations, within the role ceilings. Its configuration determines what work gets scheduled; GitHub installation access determines the maximum repository authority. The mint establishes standing repository/role authority, not proof that a particular run was admitted or remains active. It does not read the dispatcher’s configuration/database, inspect Pod ownership, query Job state, or call TokenReview.

Cluster enforcement. Tenant execution namespaces separate mint authority. Only trusted operators, the scoped dispatcher, and required Kubernetes controllers may create or mutate these identities and workloads. Restrict service-account token requests, impersonation, exec, ephemeral-container access, and namespace creation/recreation accordingly. Admission enforces approved service accounts, runner images, commands, and configuration. Restricting account creation alone is insufficient: someone who can create arbitrary Pods can select an existing service account. Agent runners and remote sandboxes must not hold those administrative capabilities. See Kubernetes workload and token-request permissions.

Expiry and cancellation. Offline JWT verification cannot immediately detect Pod/service-account deletion or run cancellation. A stolen assertion may be replayed until expiry, and an issued GitHub token has its own remaining lifetime. Keep projected tokens short-lived, audience-restricted, and only in the trusted runner. Normal cancellation stops the runner and its refresh loop and removes run credentials; it does not instantly revoke leaked tokens. Immediate revocation would require an additional mechanism. See Kubernetes offline validation limits.

  • Normalized evaluation input: current entity/activity and actor evidence prepared for selection.
  • Selected run: one authorized agent/context choice with target and output destination.
  • Job / Pod: Kubernetes workload object and its execution instance. A replacement Pod can repeat program execution.
  • Sandbox: isolated remote OpenShell workspace, distinct from the Job Pod.
  • Result: application outcome and configured output, retained independently of workload cleanup as required.

MVP invocation and scheduling contract

Use concurrencyPolicy: Forbid on each CronJob to prevent ordinary overlap within that schedule. Invocations must still be idempotent: CronJob scheduling can duplicate or miss executions, and this policy does not coordinate different CronJobs. Persisted checkpoints and pending work allow the next invocation to resume; workers must not depend on every scheduled tick occurring. Kubernetes CronJob behavior.

Bound each cycle’s batch size and runtime so it can exit even while a backlog exists. Reserve progress for both completion/cleanup and new admissions. Source discovery, dispatch, and completed-run visibility each depend on their schedule; accept minute-scale processing plus Pod startup and backlog delays for the MVP. Exact intervals, cycle limits, deadlines, and admission capacity remain configurable design choices, not a start-time guarantee.

Separate the temporary CronJob worker Jobs from the agent Jobs they create. CronJob history cleanup may remove old worker Jobs. Agent Jobs have no automatic TTL and must not carry owner references to the temporary dispatcher Job or Pod; only the dispatcher deletes them after recording outcomes. Kubernetes owner/dependent cleanup.

Two-phase deployment view

MVP: two CronJobs with PostgreSQL

Poller CronJob → observations/checkpoints in PostgreSQL → dispatcher CronJob → independent agent Jobs → remote sandbox gateway.

The poller discovers and persists a bounded batch, then exits. Each dispatcher invocation first records terminal outcomes and retries cleanup, then selects/adopts pending runs and launches eligible Jobs within configured capacity and cycle limits. It exits without waiting for agent execution. Later invocations resume from PostgreSQL and inspect retained Jobs. Filesystem manifest/configuration supplies source, authorization, and workload policy.

One selected source; one poller CronJob and one dispatcher CronJob; no separate broker or required manager process. The two CronJobs may share a service identity. Multiple concurrent workers and source partitioning are deferred.

Later: continuous dispatch and independent scaling

Partitioned pollers and optional webhook receiver → PostgreSQL → coordinated dispatch workers → agent Jobs.

If periodic dispatch becomes too slow, run the same bounded dispatcher cycle continuously in a Deployment. Polling can remain scheduled. This changes invocation frequency, not database ownership or the observe → commit → delete contract. Multiple concurrent workers additionally need database claims, coordinated checkpoints, and source partitioning; independent deployments alone do not provide safe parallel processing.

Private webhook ingestion, continuous dispatch, and multiple concurrent workers are separate extensions. Recover partial fan-out, ambiguous creates, retries, and unfinished cleanup through the same persisted records.

State, identity, and recovery

Candidate acceptance, run admission, and observation completion are distinct milestones. A producer may acknowledge a candidate only after responsibility for it can be recovered. Dispatch delivery may be acknowledged after every selected run is recoverably admitted, or a terminal no-match/rejection is recorded; this does not mean the agent work has finished. Committing observations to PostgreSQL accepts responsibility before selection. Each dispatcher invocation reads terminal Job status and determines observation completion from the recorded outcomes of all required runs.

Proposed PostgreSQL recovery store

The team has no existing PostgreSQL service, but operating one is acceptable. This proposal therefore uses PostgreSQL from the pilot onward, replacing the earlier preference for a pilot without a mandatory database. Database deployment, backup/restore, and availability arrangements still need to be specified.

The poller commits observations and their covered source checkpoint in one transaction. Advance only through source activity safely accounted for by the discovery contract; pagination failures, timestamp ties, and changing source queries must not skip observations. The checkpoint means accepted responsibility, not completed agent work. If PostgreSQL is unavailable, do not acknowledge new observations or advance the checkpoint.

The dispatcher persists the complete selected set and configuration revision before creating Jobs. Each execution attempt has a stable identity for create recovery; an intentional retry creates another attempt under the same selected run. The dispatcher cycle persists terminal outcomes, cleanup-pending state, and any pending external marker updates together before deleting Jobs. Retry Job deletion or a failed marker update independently of agent execution. PostgreSQL transactions do not include Kubernetes or source API calls; recover those effects by identity and source-specific idempotency rules.

Completion ownership and permanent failures

Agreed design direction; implementation pending. The dispatcher owns each Job from creation through status reconciliation and deletion. The runner performs its work and exits; it does not call back to the Fullsend control plane or write completion records. Kubernetes maintains Job/Pod status. The dispatcher observes that status and owns the selected-run outcome, observation-level completion decision, and any external handled marker. Agent Jobs may still make the source changes that constitute their work.

Observe, record, then delete

  1. Persist the selected run and execution attempt before launch; record the Job namespace, name, and UID when known.
  2. At each dispatcher invocation, inspect associated agent Jobs and resume pending cleanup. Bound the scan while preserving progress across invocations. A later continuous implementation may use watches; the MVP does not require completion notifications.
  3. When the Job reaches Complete or Failed, validate its association with the attempt and read the terminal status and necessary Pod diagnostics. The trusted Job entrypoint must preserve fullsend run exit status: successful exit means the configured run contract was satisfied. Artifact retention remains a separate concern.
  4. Commit the attempt outcome, selected-run state, observation aggregate, any external marker update, and cleanup-pending state to PostgreSQL. Repeated reconciliation is idempotent; an older attempt cannot overwrite a newer attempt’s outcome.
  5. After the commit is confirmed, delete the matching Job with a UID precondition and record cleanup completion. A missing Job is successful cleanup only when its outcome was already durably recorded.

Retain terminal Jobs until the dispatcher has committed their outcomes. Do not configure automatic TTL or another cleanup controller for agent Jobs that can delete them first. Keep agent Job lifetimes independent of the temporary dispatcher Job and Pod; CronJob worker history cleanup must not cascade into deleting agent Jobs. If the dispatcher or PostgreSQL is unavailable, completed Jobs remain for later reconciliation. Preserve any required diagnostics before deletion.

A permanently failed required run leaves the observation in a visible failed state awaiting explicit retry or dismissal. Retain successful sibling-run outcomes so recovery can retry unfinished work without rerunning completed work. Dismissal is recorded as an explicit disposition, not success. Retry limits, authorization for retry/dismissal, and the operator interface remain open.

Completion applies to the specific source observation or revision. It must not acknowledge newer changes to the same entity. PostgreSQL is the proposed durable state store; schema and external marker format remain open. If an agent makes an external change and then fails before successful completion, retry still needs source-specific effect idempotency or recovery.
