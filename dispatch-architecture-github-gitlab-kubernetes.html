Summary

Fullsend dispatches AI agents in response to forge events (issues, PRs/MRs, comments, labels). The two supported platforms — GitHub and GitLab — use fundamentally different dispatch architectures shaped by each platform's capabilities and constraints.

GitHub uses a hybrid of webhooks and cron schedules. The primary dispatch path is webhook-driven with sub-second latency: events flow through a workflow_call shim into a centralized dispatcher that normalizes events into a forge-neutral NormalizedEvent, mints ephemeral tokens via OIDC, and launches agent workflows. Alongside this, cron schedules drive the prioritize scheduler (issue scoring) and scribe (meeting notes → issue backlog). A planned steerwatch (ADRs 0106/0113/0119) will poll for follow-up events and absorb them mid-run, replacing the current cancel-and-re-dispatch behavior — all implementation PRs are still open. Platform-provided event integrity eliminates the need for cryptographic signing.

GitLab (current) is polling-driven with 5–15 minute latency for most events. Two cron schedules discover events, a hardcoded Go router selects stages, and API-triggered pipelines dispatch agent runs. HMAC-SHA256 signing protects the dispatcher→agent boundary because pipeline variables are user-overridable.

GitLab (ADR 0125, accepted and partially implemented) adds a webhook fast-path that triggers a native GitLab pipeline via a project trigger token. The poller becomes a backstop for missed deliveries. Foundation work has shipped (trigger-token CRUD, CAS dedup, override-role primitives); remaining work includes the dispatcher scaffold, event builder, CLI wiring, and provisioning.

Convergence: Both platforms are moving toward entity-first evaluation (ADR 0098), where agents reconcile current entity state rather than trusting only the triggering event. On GitHub this will be paired with the steerwatch (planned in-run absorption of follow-up events); on GitLab the same entity reconciliation feeds the CEL dispatch core. Event normalization into a forge-neutral NormalizedEvent is shared across both platforms via harnessdispatch.

Security Model

The platforms face different threat models because of how they expose pipeline execution. GitHub's workflow_call provides structural guarantees; GitLab requires cryptographic and procedural mitigations.

Trigger-Token Threat Model (ADR 0125, GitLab only)

The webhook fast-path introduces a trigger token — a credential weaker than the bot PAT that can start the privileged dispatcher pipeline. Mitigations:

  • Token possession = dispatcher execution capability (treat as sensitive)
  • All trigger-supplied variables validated against API re-fetches
  • HTTP clients ignore trigger-influenced proxy and CA settings
  • Webhook URLs and tokens never logged
  • Rotation and redaction procedures required

ADR Evolution

How the dispatch architecture evolved through architectural decisions.

ADR 0008 — Superseded
workflow_dispatch + PAT for cross-repo dispatch
Original GitHub dispatch used a stored PAT. Replaced by the mint model.
ADR 0028 — Deprecated
GitLab support via webhook bridge
Originally proposed an external translation bridge for GitLab webhooks. Superseded by cron-polling (ADR 0067). Credential model remains as reference.
ADR 0029 — Current
Central token mint + shared apps
Moved GitHub App PEMs to a central mint service. Accepts OIDC JWTs, verifies job_workflow_ref, returns scoped tokens. Enabled workflow_call.
ADR 0041 — Current
Synchronous workflow_call dispatch
Replaced async workflow_dispatch fan-out with synchronous workflow_call for better UI correlation. Partially superseded by CEL-based dispatch.
ADR 0054 — Current
Authorization on all dispatch paths
Requires write-level (or triage-level for observation) permission on all dispatch paths. Applies to both GitHub and GitLab.
ADR 0061 — Current
Harness CEL triggers and dispatch drivers
Harnesses declare CEL trigger expressions on a forge-neutral NormalizedEvent. Engine exists and works for GitHub + Jira; not yet wired to GitLab poller.
ADR 0063 — Current
Polling-based work discovery
fullsend poll reuses dispatch driver architecture. Poll input drivers discover changes, emit NormalizedEvent. First driver: Jira.
ADR 0067 — Current
GitLab cron-polling event dispatch
Two-path model: native merge_request_event for MRs + cron-polling for everything else. Single bot PAT, dual schedules, HMAC signing.
ADR 0098 — Current/Desired
Entity-first harness evaluation
CEL receives entity (required) + event (nullable). Polling discovers entity state without synthetic events. Partially supersedes event-only model.
ADR 0106 — Accepted, not yet implemented (GitHub)
Serialized agent runs and event coalescing
ADR accepted (PR #6909, merged). Will change GitHub concurrency from cancel-in-progress: true to false. Implementation (PR #7007) is still open. Current codebase still cancels in-flight agents.
ADR 0113 — In-flight (GitHub)
Steer running agents with mid-run updates
Instead of finishing with stale context and needing a follow-up run, a running agent absorbs new events for the same work item in-flight. Implementation (PR #6959) is still open.
ADR 0119 — In-flight (GitHub)
Steerwatch: poll platform run records for follow-up events
The steerwatch polls the shim workflow's follow-up runs created after the current run started. Effectively an in-run poller, but scoped to a single entity. Open PRs #7447–#7461.
ADR 0125 — Accepted, partially implemented (GitLab)
Hybrid GitLab dispatch (webhook + poller backstop)
ADR merged (PR #7759, Sep 28). Tracked via epic #7766 (10 issues, 3 closed). Shipped: trigger-token CRUD (#7780), CAS dedup (#7812), override-role primitives (#7813). In progress: CI_JOB_TOKEN pinning (#7817). Remaining: dispatcher scaffold, event builder, CLI wiring, install/uninstall, e2e validation.

Ship-Gating Risks

Before ADR 0125's webhook fast-path can ship, these items must be resolved.

Implementation Requirements

planned
Project-pinned API re-fetches
Fail-closed API re-fetches with action-vs-state consistency validation. Webhook payloads are untrusted hints; the dispatcher must re-derive entity state from the API and validate that claimed transitions match current snapshots.
done
Concurrency-safe dedup persists
Both the webhook dispatcher and poller write to shared dispatch state. CAS (compare-and-swap) poll-state persist shipped in PR #7812 (merged Sep 28).
planned
Dedicated webhook dispatcher CI include
The webhook-triggered dispatcher must be a separate CI include from the agent job template. This isolates the attack surface of trigger-token-initiated pipelines.
in progress
Identity pinning to CI_JOB_TOKEN
Agent and poller gates must pin identity to the unforgeable CI_JOB_TOKEN job record rather than overridable CI variables like CI_PROJECT_ID. PR #7817 is open.
done
Deny-before-admit debug-tracing guard
All fullsend jobs refuse to start under debug tracing. The CI_DEBUG_TRACE guard runs at the top of the agent template, before any token-bearing operation.
planned
Transport hardening
HTTP clients must ignore trigger-influenced proxy and CA settings. Prevents a trigger-token holder from MITM'ing API calls.
partially done
Trigger-token rotation and redaction
Trigger-token and webhook CRUD primitives shipped in PR #7780 (merged Sep 28). Remaining: install-time provisioning (#7772), operational rotation procedures, and log-redaction guarantees.

Open Risks (no solution yet)

open
API base-URL pinning
No unforgeable pin exists for the GitLab API base URL. The CI_API_V4_URL variable is overridable, meaning a trigger-token holder could potentially redirect API re-fetch calls to a malicious endpoint. This undermines the entire re-fetch trust model.
open
Snapshot-consistent replay
An attacker holding the trigger token could replay actions that still match current entity state. Polling-based event-time binding and dedup narrow this window but don't close it entirely.
